● Shipped Case 01

Pay application rebuild

Role: Owner, end to end Outcome: -92% incidents on that flow · +32% input speed

Problem

Pay applications move money between parties on a construction project, and the calculation logic behind them was producing customer-facing errors. The input flow was slow enough that people made mistakes upstream of the math. I led the rebuild end to end and instrumented both incident volume and input efficiency before shipping, so I'd know whether the fix actually worked.

Outcome

Customer-reported incidents tagged to the calculation flow fell 92% comparing equivalent periods before and after release. Input efficiency improved 32% over the same window. I tracked both on purpose, because incident volume on its own falls just as easily when people quietly abandon a workflow, and a defect count with no usage number next to it does not tell you which one happened.

● Shipped Case 02

Document extraction for migration

Role: Owner, end to end Context: production AI, regulated document domain

Problem

Finalized PDFs in our legacy product stored no structured field values. That did not make migration slow, it made it impossible: a customer moving to the newer platform mid-project had to re-key everything by hand, so most of them refused to move at all. I wrote the business case, evaluated OCR and custom PDF parsing against trained extraction models, and chose Azure Document Intelligence because OCR alone could not hold accuracy on documents where the numbers matter financially.

Outcome

A capability that was previously impossible shipped to production. I set the model strategy, one trained model per form family rather than one generalized model, on accuracy and maintainability grounds, and owned model promotion across environments, feature-flag rollout, and QA validation. The decision I would defend hardest is a cut: project team fields extracted inconsistently because a model trained on narrow layouts degrades when the layout drifts, so I removed them from extraction and left them user-editable. More training was not going to buy the customer anything they could feel.

Problem

Support agents were the search interface for questions the documentation already answered. The same forty or so questions arrived in a hundred phrasings, and every repeat pulled a subject matter expert away from work only they could do. I clustered a real ticket sample by what the resolution actually required, wrote the refusal path for anything needing legal interpretation, and ran a weekly triage on what the taxonomy didn't yet cover.

Outcome

No shareable numbers on this one. What matters more: an agent that's confidently wrong costs more than one that defers. Before launch, I wanted "correct" defined, and every refusal written as deliberately as every answer.

● Demo Case 04

PaySimple

Role: Solo build Stack: Next.js 14, TypeScript, Claude API (structured outputs), Supabase (row-level security), Vercel

Problem

Contractors pull payment terms out of contracts by hand, rebuild the schedule in a spreadsheet, and carry compliance risk they can't easily see: retainage release conditions, pay-when-paid versus pay-if-paid clauses, prompt payment law that varies by state. Generic payment software doesn't speak that language, because it wasn't built for construction contracts specifically.

Solo build, product and engineering both. The pipeline reads an uploaded contract, identifies the agreement type, and extracts payment terms and key dates using the Claude API, not a template matcher or a regex pass over the PDF text. Extracted terms feed a payment schedule that accounts for progress draws, retainage, and lien waivers, then flow into a pay application workflow with line-item management and the calculations that go with it. A compliance layer checks for the clauses that actually cause payment disputes: pay-when-paid versus pay-if-paid language, retainage triggers, completion dependencies, and state prompt payment law.

Outcome

This is a seeded demo, not a shipped product. It's seeded with a full sample contractor's book of work rather than real data, so you can click through a contract, a schedule, and a pay application without creating an account. The extraction pipeline, the schedule logic, and the compliance checks are all real and running; the audit trail around corrected drafts is what took the longest to get right.
